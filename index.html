About Me

I'm switching careers and jumping into development head-first. I can lead teams, adapt to anything, and solve problems fast when things get chaotic. What drives me is actually building something that works: something real that people can use and interact with.

I'm obsessed with building apps and interactive experiences. It started with a D&D virtual tabletop extension and a dark fantasy world to go with it, and it grew into the four projects below. I love mixing storytelling with code: taking creative ideas and turning them into working software.

Here's my learning approach: I'm learning from both ends and meeting in the middle. I build real projects with AI help, working out how each piece gets built and why it works. At the same time, I'm taking HTML, CSS and JavaScript in college, learning the fundamentals and the theory. So I'm not just following tutorials: I connect what I learn in class to what I'm building, and the other way round.

My networking classes were a game-changer for understanding how systems talk to each other. Learning new coding languages is hard for me. Syntax doesn't just click, so I practice, build actual projects, and push through the frustration. Every bug I hit, I connect back to class, and every concept from class, I try in a project. It's not the fastest way to learn, but it sticks.

Roadleaf

Offline audio reader for Android

Public

Built with: Kotlin, Jetpack Compose, Room, Media3, Android TextToSpeech

  1. Original idea

    Listen to books, web serials and my own stories hands-free while driving, using the voices already on my phone: no cloud narration, subscription or account.

  2. Problems

    One flat voice made long sessions tiring and characters blurred together. Web pages were full of menus and ads, phone calls and car audio had to pause and resume correctly, and native voice engines crashed the app until the playback path was fixed.

  3. What I learned

    How an Android app is put together: screens in Compose, a Room database, Media3 playback and audio focus. Also that a reader should only read what your account can see, and never work around paywalls or sign-ins.

  4. Where it is now

    Imports EPUB and TXT, reads any secure webpage and turns chapters itself, and gives characters their own voices as it learns them. Drive view, Android Auto and a battery saver are built in, with test builds on GitHub. 55 commits since November 9, 2026.

  5. End goal

    Listening that feels like someone reading to you, and the place where finished, approved chapters from the Reality Engine are read.

Forever DM Combat

D&D combat extension for Owlbear Rodeo

Public

Built with: React, TypeScript, Vite, Owlbear Rodeo SDK

  1. Original idea

    Running combat for my dark fantasy campaign, The Broken Chain, was slow: HP, initiative and actions for every player and monster. I wanted a virtual tabletop extension that tracks the table so the DM can run it.

  2. Problems

    Two browsers could disagree about a creature's HP. The player view could leak DM-only information. Features got rebuilt twice because nobody checked whether they already existed, and the first version got tangled enough that I started a clean rebuild in June 2026.

  3. What I learned

    Decide where each fact lives by who needs to see it: shared room state with one writer (the DM), live broadcasts, and private browser storage. Keep the engine, the D&D rules and the campaign content in separate layers, and check a build before trusting it.

  4. Where it is now

    Version 0.8.80, with 818 commits since June 5, 2026. A main popover, DM panel, combat window, character and creature pop-outs, level-up flow and player tracker. It tracks, shows and rolls; it never resolves a turn for you.

  5. End goal

    An engine that can run any d20 game through modules, with The Broken Chain as its first full campaign, ready for my group at the table.

Unified AI Dashboard

Black Hole workstation: one local control center for AI work

Private · in development

Built with: Python, SQLite, HTML, CSS, JavaScript

  1. Original idea

    I use Claude, Codex, ChatGPT, Gemini and OpenCode for different jobs, each with its own window, account and history. I kept asking "where did we leave that file or decision?", so the idea was one local workspace that remembers where the work actually stands.

  2. Problems

    Which file is the real one, when a newer date doesn't mean approved? Why explain the same project twice? What did all those model calls actually cost? And how do I tell a real feature from a promising screen?

  3. What I learned

    Finding a file isn't verifying it. Continuing a session needs storage, checks and recovery, not just a summary. Honest measurement leaves unknown numbers unknown. And designed, coded, tested offline and working live are four different milestones.

  4. Where it is now

    A real local app: a Python service with SQLite and a browser interface. It has project records, a task controller, conversations filed by topic, a usage dashboard per account, and a 13-seat station map with checked job delivery for two seats. 23 test suites pass locally; some AI connections are still only partly qualified.

  5. End goal

    A normal multi-hour session that saves its work, tracks usage, safely changes context and resumes without rebuilding the conversation. After that, a full story chapter carried from Generator to Reviewer.

Reality Engine

A system that remembers and manages a whole fictional world

Private · in design

Built on: the Unified AI Dashboard's task controller and Black Hole seats

  1. Original idea

    I wanted to write Meridian, an ongoing sci-fi story with crews, ships, rival factions and relationships, where choices still matter chapters later instead of disappearing the next time I ask a model to write.

  2. Problems

    A model could write a good scene and still get the world wrong: a character knowing something they never saw, or forgetting their own history. One model judging its own work missed things, and failed drafts threw away good ideas.

  3. What I learned

    The ideas behind state management, access control and structured memory: what the world knows is different from what each character knows. What a model writes is different from what the system accepts. And the worker who says "I finished" shouldn't also approve their own work.

  4. Where it is now

    The design is documented: role boundaries, alternate timelines, world-state permissions and publication gates. The worker handoff is tested offline, with job cards, delivery folders for two seats and file checks. Automatic workers and full chapter publishing aren't live yet.

  5. End goal

    One complete chapter run: a Generator writes, Canon and Behavior check it, a Reviewer approves the exact version, a Fixer repairs a permitted seam, and the Director releases the chapter with a matching world-state lock. Readers get only the approved release.

No public repository yet: the design and the offline-tested handoff live inside the dashboard project.
